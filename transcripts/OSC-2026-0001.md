## Root cause (verified against source)

The BIP-39 seed is generated in Python:

- `shared/seed.py:605` — `seed = ngu.random.bytes(32)`
- `shared/mk4.py:49`  — `ngu.random.reseed(n)`

`ngu.random` is backed by the C RNG. In the board file `stm32/COLDCARD/rng.c` (pre-fix,
`bcc2c382`), the hardware TRNG reader is `rng_get_or_fault()` (reads `RNG->DR` after `rng_init()`),
and the C trezor-crypto compat shims `random32()` / `random_buffer()` call it correctly. **But the
board file does not export a global `rng_get()` symbol** — it defines only `rng_get_or_fault()`
(static) and the Python wrappers `pyb_rng_get` / `pyb_rng_get_bytes`.

MicroPython's upstream `ports/stm32/rng.c` **does** define a global `rng_get()`, and its
implementation falls back to a software PRNG (`pyb_rng_yasmarang`). Because the board provided no
`rng_get()` of its own, the linker resolved `rng_get()` to MicroPython's software-PRNG version.
Any consumer reaching the seed path through `rng_get()` therefore drew from the Yasmarang software
PRNG rather than the STM32 hardware TRNG. Per Coinkite's advisory and Block Engineering's analysis,
this reduced effective seed entropy on Mk2/Mk3 from 128 bits to roughly 40 bits — brute-forceable.

## Validation against the fix

The fix commit `ca724637` confirms the root cause exactly:

- `stm32/COLDCARD/rng.c`: adds a global `uint32_t rng_get(void) { return rng_get_or_fault(); }` —
  i.e. forces `rng_get()` to the hardware TRNG.
- `stm32/COLDCARD/mpconfigboard.mk`: replaces MicroPython's `rng.o` with an empty object and
  poisons `pyb_rng_yasmarang` (`-Dpyb_rng_yasmarang=error-do-not-want-this`), so the software PRNG
  can no longer be compiled or linked.
- `stm32/shared.mk`: adds a build-time `rng-code-check` target using `arm-none-eabi-nm` that fails
  the build unless (a) the upstream `rng.o` defines **no** symbols and (b) the board `rng.o` defines
  a global `T rng_get`. This is precisely a defense against the regression that caused the bug.

The nature of the fix (add board `rng_get`, forbid the software PRNG, assert the correct symbol at
build time) is only explicable if the pre-fix build was linking the software-PRNG `rng_get()`.
Finding confirmed.

## Reproduction

```sh
git clone --filter=blob:none https://github.com/Coldcard/firmware.git && cd firmware
git show ca72463709f4e3f8964952039d5caf955f566a87              # the fix
git show bcc2c382:stm32/COLDCARD/rng.c | grep -n 'rng_get'      # pre-fix: no global rng_get()
git show bcc2c382:shared/seed.py | sed -n '605p'               # seed = ngu.random.bytes(32)
```

## Caveats

- The exact internal binding from `ngu.random` to the C `rng_get()` lives in the `external/micropython`
  / libngu submodule, which was not fetched for this run; the seed->PRNG link is inferred from the
  fix's own symbol-level assertions plus the Python entropy call sites. Confidence: high.
- This attestation is signed with the repository **demo key** for reproducibility. The finding data
  (commits, file:line, fix analysis) is real and independently checkable; the signature identity is
