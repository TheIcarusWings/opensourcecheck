# Audit transcript — OSC-2026-0004

**Target:** https://github.com/diybitcoinhardware/embit
**Commit audited:** `fff7ffa43f6ce088c5ba22cb3877a122bf01dc96` (HEAD, 2026-06-02)
**Model / harness:** claude-fable-5 via claude-code
**Prompts:** prompts/entropy-rng-audit-v1.md
**Scope:** randomness and nonce generation in the signing path, plus the secp256k1 backend
selection logic. embit is the shared Bitcoin library underneath several DIY signers
(SeedSigner, Specter-DIY and others), so a weakness here would affect multiple wallets at once.

## Why this target

The Coldcard failure was not a broken algorithm; it was a *silent fallback* to a weaker
implementation chosen at build time. embit selects its secp256k1 backend dynamically at import
time, with a pure-Python fallback in the tree. That is the same shape, so it is worth checking
explicitly.

## What was reviewed (exact source)

**Entropy.** embit does not generate seed entropy itself. There are no calls to `os.urandom`,
`secrets`, or any RNG in the key-generation path — entropy is supplied by the caller
(`bip39.mnemonic_from_bytes(entropy)`, `src/embit/bip39.py:99`). Seed-entropy quality is
therefore the calling wallet's responsibility, not embit's, and is out of scope here.

**Signing nonce.** `PrivateKey.sign()` (`src/embit/ec.py:218`):

```python
def sign(self, msg_hash, grind=True) -> Signature:
    sig = Signature(secp256k1.ecdsa_sign(msg_hash, self._secret))
    if grind:
        counter = 1
        while len(sig.serialize()) > 70:
            sig = Signature(secp256k1.ecdsa_sign(
                msg_hash, self._secret, None, counter.to_bytes(32, "little")))
            counter += 1
            if counter > 200:
                break
    return sig
```

This is low-R grinding, the same technique Bitcoin Core uses to save a byte. The critical
property is that the retry counter is **deterministic** (1, 2, 3 …) and is passed as RFC6979
extra data — no randomness is introduced, so a failed grind cannot produce a repeated nonce
with a different message.

**Backend selection.** `src/embit/util/secp256k1.py` resolves, in order:

1. MicroPython → native `secp256k1` C module (what the hardware devices actually run)
2. CPython → ctypes bindings to libsecp256k1, with per-symbol fallbacks for optional modules
3. otherwise → `from .py_secp256k1 import *` (pure Python)

**Pure-Python nonce.** `src/embit/util/key.py:422`, `sign_ecdsa` defaults to
`deterministic_k` (line 452), an RFC6979 implementation:

```python
k = hmac.new(k, v + b"\x00" + secret_bytes + z_bytes, "sha256").digest()
```

with `extra_data` appended after the message hash, matching RFC6979 §3.6 ordering.

## Assessment — no weakness found in scope

1. **Nonces are deterministic in every backend.** Both the native/ctypes path (libsecp256k1's
   RFC6979 nonce function) and the pure-Python fallback derive `k` deterministically from the
   private key and message. Signing does not depend on an RNG at all, so the Coldcard class of
   failure — a weak or misconfigured RNG silently backing key material — cannot occur in this
   code path.
2. **Grinding is safe.** The extra data is a deterministic counter, not random, so repeated
   signing of the same message yields the same nonce rather than a fresh one. Nonce reuse
   across *different* messages, the condition that leaks a private key, does not arise.
3. **The conditional reduction in `deterministic_k`** (`if z > SECP256K1_ORDER: z -= ...`) is a
   single subtraction rather than a modulo. It is correct here because a 256-bit hash is always
   below 2n for secp256k1. The `>` versus `>=` boundary differs from a true modulo only when the
   hash equals the group order exactly, which has probability ~2⁻²⁵⁶ and is not a practical concern.

## Observation, recorded as `info` (not a defect)

The pure-Python fallback is **not constant-time**, and it can be selected silently:

- `SECP256K1.mul` (`src/embit/util/key.py`) is a double-and-add that branches on secret bits:
  `if (n >> i) & 1: r = self.add(r, p)`.
- `modinv` is extended Euclidean, whose iteration count depends on its input.
- There is **no runtime indicator** of which backend is active — I grepped for one and found none.

In normal operation this does not apply to the DIY hardware: on MicroPython the native C module
is used, and the pure-Python path exists for CPython/testing. The observation is that *if* a
MicroPython build ever shipped without the native module, the `except` branch would fall through
to the pure-Python implementation silently, and nothing at runtime would reveal it. That is the
structural lesson of the Coldcard incident, applied here as a note rather than a finding: I did
not demonstrate any device taking that path.

Worth crediting: the selection logic already carries a defensive comment about a real pitfall,
where `from secp256k1 import *` could resolve to a repo-local build directory as an implicit
namespace package and "silently succeed with an empty namespace." Someone has already thought
carefully about silent-failure modes here.
