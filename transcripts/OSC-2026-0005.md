# Audit transcript — OSC-2026-0005

**Target:** https://github.com/KeystoneHQ/keystone3-firmware
**Commit audited:** `31f1fa88a522f492b9ad6260c4c3e316bd209b32` (HEAD, 2026-08-04)
**Model / harness:** claude-fable-5 via claude-code
**Prompts:** prompts/entropy-rng-audit-v1.md
**Scope:** the seed-entropy generation path on a live, funds-holding commercial hardware
wallet — the exact question the Coldcard incident raised: where does seed entropy come from,
can it silently degrade, and can it leak.

## What was reviewed (exact source)

**`GenerateEntropy`** — `src/managers/keystore.c:75`, the function behind wallet creation
(reached from `ModelGenerateEntropy`, `src/ui/gui_model/gui_model.c:427`):

```c
HashWithSalt(inputBuffer, (uint8_t *)password, ..., "generate entropy");

SE_GetTRng(randomBuffer, ENTROPY_MAX_LEN);                 // 1: MCU TRNG
hkdf(inputBuffer, randomBuffer, outputBuffer, ITERATION_TIME);
memcpy_s(inputBuffer, ..., outputBuffer, ENTROPY_MAX_LEN);

ret = SE_GetDS28S60Rng(randomBuffer, ENTROPY_MAX_LEN);     // 2: DS28S60 secure element
CHECK_ERRCODE_BREAK("get ds28s60 trng", ret);
hkdf(inputBuffer, randomBuffer, outputBuffer, ITERATION_TIME);
memcpy_s(inputBuffer, ..., outputBuffer, ENTROPY_MAX_LEN);

ret = SE_GetAtecc608bRng(randomBuffer, ENTROPY_MAX_LEN);   // 3: ATECC608B secure element
CHECK_ERRCODE_BREAK("get 608b trng", ret);
hkdf(inputBuffer, randomBuffer, outputBuffer, ITERATION_TIME);

memcpy_s(entropy, entropyLen, outputBuffer, entropyLen);
```

**`TrngGet`** — `src/driver/drv_trng.c:12`, reads the MH1903 hardware TRNG in 16-byte blocks,
blocking until each block is ready (`while (0 != TRNG_Get(buf4, TRNG0));`).

**Debug macro** — `src/managers/keystore.c:36-42`.

## Assessment — no weakness found in scope

1. **Three independent hardware entropy sources, not one.** Seed entropy is derived from the
   MCU TRNG *plus* two separate secure elements (DS28S60 and ATECC608B), each folded in through
   a separate HKDF step with the running value chained forward. This is the specific mitigation
   Coldcard lacked: there, a single source was silently swapped for a software PRNG and nothing
   else contributed. Here, compromising or degrading any one source still leaves two independent
   hardware sources feeding the KDF chain.
2. **A password-derived salt seeds the chain.** `HashWithSalt(...,"generate entropy")` sets the
   initial input from the user's password, so the output is not a pure function of device RNGs.
3. **Secrets are not leaked through debug output.** Every raw-entropy print is wrapped in
   `KEYSTORE_PRINT_ARRAY`, which is defined as an empty macro because `KEYSTORE_DEBUG` is
   hardcoded to `0` (`keystore.c:36`). Importantly this is a *source constant*, not a build flag
   — a build configuration cannot silently enable it, which is precisely the failure shape that
   caused the Coldcard bug (`MICROPY_HW_ENABLE_RNG=0` came from the build, not the source).
4. **Buffers are cleared.** `CLEAR_ARRAY` is applied to all three working buffers on exit,
   including on the error path, since it sits after the `do { } while (0)` block.

## Observation, recorded as `info` (not a defect)

Error handling across the three sources is asymmetric. `SE_GetDS28S60Rng` and
`SE_GetAtecc608bRng` are both checked with `CHECK_ERRCODE_BREAK`, but the return value of
`SE_GetTRng` is not checked. If that first call failed, `randomBuffer` would be mixed in
containing whatever it held previously.

This is not exploitable as written: the two checked sources are still mixed in afterwards, so
the final entropy retains at least two independent hardware inputs, and a failure of the later
sources aborts via `CHECK_ERRCODE_BREAK`. It is recorded only because consistent error checking
on all three would make the "at least N good sources" property explicit rather than incidental.

## Amendment — 2026-08-04

**Correction to the scope of this record.** The original stated that the MH1903 TRNG driver
(`src/driver/drv_trng.c`) was in scope, which implied its status and error handling had been
reviewed. `TrngGet` was read, but its handling of the TRNG's **status/attack bits** was not
examined.

A later independent audit by a different model (`OSC-2026-0017`) observed that `TrngGet` spins
on `TRNG_Get` without ever inspecting the MH1903 TRNG ATTACK status bit, while the vendor's own
`external/mh1903_lib/.../mh_rand.c` does check it
(`if (MH_TRNG->RNG_CSR & MH_TRNG_RNG0_CSR_ATTACK_Mask)`, under the comment "check if the TRNG is
attacked"). I verified that observation against source and it is correct.

The residual risk remains low for the reason this record already gives: `GenerateEntropy` mixes
two further independent hardware sources through HKDF, so a degraded MCU TRNG does not by itself
determine the seed. But the record should not have implied the driver's status handling was
checked when it was not.

The scope field has been narrowed accordingly and this attestation re-signed. The original
version remains in git history.
