# Audit transcript — OSC-2026-0007

**Target:** https://github.com/rust-bitcoin/rust-secp256k1
**Commit audited:** `9fc86f756f0cd24a5167c131551b31b748c8cdb3` (HEAD, 2026-03-01)
**Model / harness:** claude-fable-5 via claude-code
**Prompts:** prompts/entropy-rng-audit-v1.md
**Scope:** ECDSA nonce generation in the signing path.

## Why this target

These are the Rust bindings to libsecp256k1, sitting underneath BDK, LDK, Liana and most of the
Rust Bitcoin ecosystem. A nonce defect here would leak private keys across many wallets at once,
which makes it the highest-leverage target in that stack.

## What was reviewed (exact source)

`src/ecdsa/mod.rs`. Both signing entry points pass libsecp256k1's deterministic nonce function
explicitly:

```rust
ffi::secp256k1_nonce_function_rfc6979    // src/ecdsa/mod.rs:249 and :302
```

The documented API distinguishes `sign_ecdsa` (RFC6979 nonce) from the variant that additionally
accepts caller-supplied extra data, described in the source as being for the case where
"signatures are needed for the same Message and SecretKey while still using RFC6979"
(`src/ecdsa/mod.rs:271`).

## Assessment — no weakness found in scope

1. **Nonces are RFC6979-deterministic, not random.** Both call sites pin
   `secp256k1_nonce_function_rfc6979`. Signing therefore does not consume an RNG at all, so the
   entire class of failure behind the Coldcard incident — a weak or silently-substituted random
   source backing key material — cannot occur on this path.
2. **The extra-data variant preserves determinism.** Supplying extra data changes the derived
   nonce but keeps it a deterministic function of (key, message, extra data). It does not
   introduce randomness, so it cannot produce a repeated nonce across different messages, which
   is the condition that leaks a private key.
3. **No fallback implementation exists.** Unlike embit (OSC-2026-0004), these bindings delegate
   to libsecp256k1 with no pure-Rust fallback path that could be selected silently, so there is
   no equivalent silent-degradation risk.

## Scope boundary, stated plainly

This audit covers the **bindings**, not libsecp256k1 itself. The correctness of
`secp256k1_nonce_function_rfc6979` is a property of the upstream C library
(`bitcoin-core/secp256k1`), which was not reviewed here and would be a separate attestation. What
is established here is that the Rust layer selects the deterministic nonce function and does not
introduce randomness of its own.
