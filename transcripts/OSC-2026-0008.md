# Audit transcript — OSC-2026-0008

**Target:** https://github.com/KeystoneHQ/keystone3-firmware
**Commit audited:** `31f1fa88a522f492b9ad6260c4c3e316bd209b32` (HEAD, 2026-08-04)
**Model / harness:** claude-fable-5 via claude-code
**Prompts:** prompts/tx-authorization-audit-v1.md
**Scope:** the transaction-authorization loss-of-funds class. This is a **second, different
lens** on a target already audited for entropy in OSC-2026-0005; it is a separate record, not a
replacement, because a clean entropy audit says nothing about change-output handling.

## Applicability

The pack requires stating which checks do not apply. All seven apply here: this is a signer that
parses hostile PSBTs, decides which outputs are its own, computes a fee, and renders both to a
user. Firmware update integrity was not examined in this run and is excluded from scope below.

## 1. Change-output verification — correctly independent

Bitcoin PSBT logic lives in `rust/apps/bitcoin/`; the C GUI renders structs produced there.

**Single-sig** (`rust/apps/bitcoin/src/transactions/psbt/wrapped_psbt.rs`, `parse_my_output`,
~lines 1086–1148). The device does not trust the PSBT's claim. It re-derives the public key from
**its own xpub** and rebuilds the expected script for the declared purpose:

```rust
let public_key = derive_public_key_by_path(xpub, parent_path, &_child_path)?;
let expected_script = match parent_path.into_iter().next() {
    Some(ChildNumber::Hardened { index: 44 }) => ScriptBuf::new_p2pkh(...),
    Some(ChildNumber::Hardened { index: 49 }) => { /* p2sh-p2wpkh */ }
    Some(ChildNumber::Hardened { index: 84 }) => ScriptBuf::new_p2wpkh(...),
    _ => return Ok(None),
};
if expected_script != tx_out.script_pubkey {
    return Ok(None);          // not mine -> shown as a payment, not as change
}
```

The failure mode is safe: an output that does not reconstruct is returned as `None`, so
`is_mine` is false and it is displayed as a payment to a stranger rather than hidden as change.
An attacker labelling their own address as change cannot make it display as change.

**Multisig** (same function, ~lines 998–1083). The whole script is rebuilt from **every**
cosigner, not merely the device's own key:

```rust
if bip32_derivation.keys().len() as u32 != total { return Ok(None); }
// fingerprint set must equal the wallet's cosigner set
if !wallet_xfps.eq_ignore_ascii_case(&xfps) { return Ok(None); }
for item in config.xpub_items.iter() {
    let derived_pk = derive_public_key(&item.xpub, &format!("m{suffix}"))?;
    pubkeys.push(bitcoin::PublicKey::new(derived_pk));
}
pubkeys.sort();
// ... build m-of-n, wrap per P2SH / P2WSH / P2SH-P2WSH ...
if expected_script != tx_out.script_pubkey { return Ok(None); }
```

This closes cosigner substitution: the derived fingerprint set must match the stored wallet
config, and the script is rebuilt from the stored xpubs rather than from PSBT-supplied ones.

## 2. Input value and fee

The device cross-checks the two sources of an input's value when both are present, and refuses
the transaction if they disagree (`get_input_prevout`, ~lines 497–535):

```rust
if let Some(witness_prevout) = &input.witness_utxo {
    if let Some(prevout) = non_witness_prevout {
        if prevout != witness_prevout {
            return Err(BitcoinError::InputValueTampered(...));
        }
    }
    return Ok(witness_prevout);
}
```

There is also a dedicated check citing the Trezor advisory by URL
(`check_my_input_value_tampered`, ~lines 591–607), and the non-witness path validates that the
supplied previous transaction actually hashes to the referenced txid.

Fee handling (`rust/apps/bitcoin/src/transactions/parsed_tx.rs`, `normalize`, ~lines 212–250):
the transaction is rejected outright if inputs total less than outputs (absent `ANYONECANPAY`),
the fee is surfaced to the user, and a large-fee warning fires above **5,000,000 sats** or
**100 sat/vByte** (verified at `parsed_tx.rs:237-244`).

## Observation, recorded as `info` — stated with its limits

`non_witness_utxo` is **not required**. Grepping the file shows it referenced only in optional
`if let Some(...)` positions (lines 166, 504, 593). When a PSBT input supplies only
`witness_utxo`, the declared amount is taken on trust and `check_my_input_value_tampered`
returns `Ok(())` without comparing anything, because its guard requires *both* fields:

```rust
if let (Some(prev_tx), Some(utxo)) = (&input.non_witness_utxo, &input.witness_utxo) {
```

I am **not** reporting this as a vulnerability, and the reasoning matters more than the
conclusion. For SegWit v0, BIP-143 commits the input amount into the sighash, so a signer that
is lied to about an amount produces a signature that is simply invalid for the real UTXO — the
transaction does not confirm and no funds move. The historical Trezor attack needed more than a
single lie: it depended on combining signatures obtained across separate signing sessions with
inconsistent declared amounts. I did not attempt to construct that scenario against this
firmware, and the large-fee warning plus the mandatory inputs≥outputs check further narrow it.

What would change this assessment: a demonstration that the device can be induced to sign the
same input twice with different declared values across sessions, with the results combinable
into one valid high-fee transaction. That is a dynamic test, not a source read, and it is
outside this run's scope. Confidence that this is *not* a straightforward vulnerability: high.
Confidence that it is fully safe under all multi-session flows: medium.

Recording it as `info` rather than silently omitting it is the point — a future auditor with a
device can settle it.

## Amendment — 2026-08-04

**Correction to the scope of this record.** As originally published, the scope field described
"the transaction-authorization loss-of-funds class" for this firmware without stating which
transaction path was examined. That overstated the coverage.

What was actually examined: **the PSBT path only** — `rust/apps/bitcoin/src/transactions/psbt/`
(`wrapped_psbt.rs`) and the shared fee logic in `parsed_tx.rs`.

What was **not** examined: the **legacy raw-transaction (companion-app protobuf) path** at
`rust/apps/bitcoin/src/transactions/legacy/`, which is a separate, live dispatch arm — `TxData`
implements `TxChecker` alongside `WrappedPsbt` in `transactions/tx_checker.rs`.

This matters because a later independent audit of that legacy path, by a different model, found
a finding there. That record is `OSC-2026-0020`, and its body is withheld pending vendor
disclosure. Nothing in the present record was wrong about the PSBT path; the error was implying
the whole class had been covered when one of two paths had not been opened.

The scope field has been narrowed accordingly and this attestation re-signed. The original
version remains in git history.
