## Assessment — no weakness found, and the design is the strongest in this series

1. **Multiple hardware sources, combined by XOR.** MCU RNG, then XOR with the Optiga secure
   element, then XOR with Tropic where present. XOR is the correct combiner: if *any* one input
   is genuinely random and independent of the others, the output is random. An attacker must
   compromise every source simultaneously, not merely one.
2. **It fails closed.** If a secure-element RNG call fails, `rng_fill_buffer_strong` returns
   `false` and the Python layer raises rather than continuing. This is the exact property
   Coldcard lacked, where a degraded source silently produced a usable but weak seed. It is also
   stricter than Keystone3 (OSC-2026-0005), which mixes three sources but does not check the
   first one's return value.
3. **The host cannot choose the seed, and neither can the device alone.** The final secret is
   `sha256(int_entropy || ext_entropy)` truncated to strength, so a malicious host supplying
   chosen `ext_entropy` still cannot determine the result without knowing the device's 32 bytes.
4. **There is a commitment protocol against a malicious device.** With `entropy_check`, the
   device publishes `hmac(SHA256, int_entropy, b"")` *before* receiving the host's entropy. The
   host can therefore verify afterwards that the device did not grind its internal entropy after
   seeing the external value. This defends against a backdoored device biasing the seed toward
   something the vendor can predict — a threat model most of the wallets audited in this series
   do not address at all.

## Observation, recorded as `info` (not a defect)

The "strong" guarantee is **compile-time conditional**. If a build defines neither `USE_OPTIGA`
nor `USE_TROPIC`, both XOR blocks compile out and `rng_fill_buffer_strong` reduces to
`rng_fill_buffer` while still returning `true` — the caller cannot distinguish "strengthened by a
secure element" from "MCU RNG alone".

This is not the Coldcard failure. There, a build flag silently substituted a *software PRNG* for
a hardware TRNG. Here the fallback is still a hardware RNG, and the conditional exists because
some Trezor models genuinely have no secure element. It is recorded because the *name* of the
function promises a property that the build configuration can remove, and a reader auditing a
specific build should confirm which flags were set rather than trusting the call site.
