# Audit transcript — OSC-2026-0026

**Target:** https://github.com/proto-at-block/bitkey
**Commit audited:** `cf16705543d0c66ff982635733d380944cc2677d` (HEAD, 2026-08-02)
**Model / harness:** claude-fable-5 via claude-code
**Prompts:** prompts/entropy-rng-audit-v1.md
**Scope:** the master-seed entropy path in the device firmware.

## What was reviewed (exact source)

**Seed creation** — `firmware/lib/wallet/src/seed.c`, `master_key_lazy_init`:

```c
bool seed_loaded = wkek_read_and_decrypt(SEED_PATH, seed->bytes, sizeof(seed->bytes));

if (!seed_loaded) {
  ASSERT(crypto_random(seed->bytes, sizeof(seed->bytes)));
}

if (!bip32_derive_master_key(seed->bytes, sizeof(seed->bytes), master_key)) {
  return SEED_RES_ERR_MASTER_DERIVE;
}

if (!seed_loaded && !wkek_encrypt_and_store(SEED_PATH, seed->bytes, sizeof(seed->bytes))) {
  return SEED_RES_ERR_SEED_WRITE;
}
```

**The RNG itself** — `firmware/lib/crypto/src/efr32/secure_rng.c`:

```c
bool crypto_random(uint8_t* data, uint32_t num_bytes) {
  if (!data || num_bytes == 0)
    return false;

  sl_se_command_context_t cmd_ctx = {0};
  sl_status_t status = sl_se_init_command_context(&cmd_ctx);
  if (status != SL_STATUS_OK) {
    return false;
  }
  if (sl_se_get_random(&cmd_ctx, data, num_bytes) != SL_STATUS_OK) {
    return false;
  }

  return true;
}
```

## Assessment — no weakness found in scope

1. **Entropy comes from a secure element, not the application MCU.** `sl_se_get_random` is the
   Silicon Labs Secure Engine RNG on the EFR32. There is no software PRNG anywhere in this path
   and no fallback to one, so the Coldcard failure class cannot occur here.
2. **It fails closed, and hard.** `crypto_random` returns `false` on *any* error — a failed
   command-context init as well as a failed random draw — and the caller wraps it in `ASSERT`.
   A failure therefore halts the device rather than proceeding with whatever happened to be in
   the buffer. This is the strictest failure handling of the wallets audited in this series:
   Trezor raises (OSC-2026-0025), Keystone3 continues with two remaining sources
   (OSC-2026-0005), and Coldcard silently produced a weak seed.
3. **The seed is encrypted at rest.** It is stored via `wkek_encrypt_and_store` under the wallet
   key encryption key rather than written in the clear, and the load path is
   `wkek_read_and_decrypt`. Generation only happens when no seed could be decrypted, so a
   working device does not silently re-roll its seed.

## Observations, recorded as `info` (not defects)

**Single entropy source.** Unlike Trezor, which XORs the MCU RNG with one or two secure-element
RNGs (OSC-2026-0025), and Keystone3, which chains three sources through HKDF (OSC-2026-0005),
Bitkey draws the seed from one source. If that secure element's RNG were biased or backdoored,
nothing else contributes.

This is a legitimate design position rather than a flaw — the Secure Engine is a certified part
and the code fails closed on any error — but it is a materially different trust assumption from
the multi-source designs, and a reader comparing these wallets should see it stated.

**Seed size not verified.** `seed->bytes` is sized by `seed_t`, whose definition I was unable to
retrieve from the blobless clone. I therefore make **no claim** about the seed length or whether
it meets the 128/256-bit target. That gap should be closed before this record is relied upon for
entropy sizing; the RNG source and failure handling above are verified independently of it.
