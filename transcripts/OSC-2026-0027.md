## 3.1 Seed / key entropy call chain (device)

**BIP-39 / SLIP-39 wallet creation**

- `core/src/apps/management/reset_device/__init__.py:88` — internal entropy is  
  `int_entropy = random.bytes(32, True)` (`strong=True`).
- Host may contribute `ext_entropy` via `EntropyAck` (`:103`).
- Combined at `:343–356` by  
  `SHA256(int_entropy || ext_entropy)` then truncated to `strength_bits/8` (128 or 256 for BIP-39).  
  Host-controlled external bytes cannot reduce security below the 256-bit internal contribution before truncation; truncation to 128 bits for a 12-word mnemonic is intentional BIP-39 strength selection, not an entropy bug.

**`random.bytes(..., strong=True)` binding**

- `core/embed/upymod/modtrezorcrypto/modtrezorcrypto-random.h:57–61` — strong path calls  
  `rng_fill_buffer_strong`; failure raises `RuntimeError` (“Failed to get strong randomness.”) — fail-closed, no silent software fallback.
- Non-strong path (`:63–64`) uses `rng_fill_buffer` only (still the MCU TRNG on device).

**`rng_fill_buffer_strong`**

- `core/embed/sec/rng/rng_strong.c:37–71` — when `USE_OPTIGA` and/or `USE_TROPIC` are defined:  
  1. fill from MCU TRNG via `rng_fill_buffer`;  
  2. XOR-mix Optiga and/or Tropic TRNG blocks;  
  3. return `false` if an SE read fails.
- `:74–78` — without Optiga/Tropic (e.g. models that do not declare those board features, such as T2T1 board TOMLs with no `[optiga]` section): strong path is still pure MCU TRNG. That is single-source hardware entropy, not a software PRNG.

**MCU TRNG**

- `core/embed/sys/rng/stm32/rng.c:32–38` — `rng_init` enables the STM32 RNG peripheral (`RNG_CR_RNGEN`).
- `:40–50` — `rng_read_u32` waits until `RNG_SR_DRDY` with neither seed nor clock error bits set (`SECS | CECS`), then reads `RNG->DR`.
- `:47–49` — FIPS continuous RNG test: reject consecutive identical 32-bit samples when `compare_previous` is set.
- `:66–79` — `rng_fill_buffer` fills entirely from that path.
- `:85` — `random_buffer` (trezor-crypto) is a thin wrapper over `rng_fill_buffer` on this build.

**Critical secrets beyond wallet seed**

- Master key material in OTP: `core/embed/sec/secret_keys/stm32u5/secret_keys.c` (and F4 counterpart) call `rng_fill_buffer_strong` when first writing master keys — same multi-source path when SE chips are present.

## 3.2 / 3.3 Hardware vs software PRNG and build flags

**Insecure LCG (production-blocked)**

- `crypto/rand_insecure.c:26–50` — under `USE_INSECURE_PRNG`, `random_buffer` is a 32-bit LCG (`1664525 * seed + 1013904223`), seeded only via `random_reseed`. Marked with a compile `#pragma message` that it is not for production.
- `core/embed/crypto/Cargo.toml:34` — feature `emulator` enables `insecure_prng`.
- `core/embed/crypto/build.rs:198–205` — `add_insecure_prng` **bails** if `feature = "production"` (unless rust-analyzer), so the LCG cannot be compiled into production firmware builds.
- `core/embed/sys/rng/unix/rng.c:27–40` — emulator: either insecure PRNG or `/dev/urandom`; not a device firmware path.

**Legacy (T1) device vs emulator**

- `legacy/Makefile.include:107–109` — `USE_INSECURE_PRNG=1` only when `EMULATOR=1`.
- `legacy/firmware/Makefile:86–87` — `rand_insecure.o` only for emulator.
- `legacy/Makefile` (non-emulator) links `rng.o`; `legacy/rng.c:27–46` reads STM32 F2 hardware `RNG_DR` with a consecutive-value check.
- Device T1 seed reset uses `random_buffer` → hardware TRNG (`legacy/firmware/reset.c` call sites via search).

**No Coldcard-class silent disable flag**

- Searched for flags analogous to `MICROPY_HW_ENABLE_RNG=0` that would swap device `rng_fill_buffer` to a software PRNG: none found for production device images. The only software PRNG is explicitly gated to emulator/test.

## 3.4 PRNG seeding sources

- Device cryptographic path does not seed a long-lived software CSPRNG for keys from chip UID/timers.
- Legacy storage-salt path (`core/embed/sec/storage/stm32u5/storage_salt.c:60–88`, non–master-key-slot branch) mixes UID + OTP randomness for **storage salt**, not BIP-39 seed material. Out of scope for seed entropy, recorded for completeness only.

## 3.5 Fallbacks, reseeding, health tests

- MCU TRNG: busy-wait on `DRDY` with SECS/CECS filter; FIPS continuous equal-sample reject (`stm32/rng.c:44–49`). On hard TRNG failure the device hangs rather than falling back to a weak PRNG — availability risk, not silent entropy degradation.
- Strong path: SE failure returns `false` → Python exception; no XOR-with-zero / continue.
- No online NIST SP 800-90B health test suite observed beyond the continuous equal-value check; hardware SE quality is trusted via driver return codes.

---

## 3.6 Signing nonces

- `crypto/options.h:58–59` — `USE_RFC6979` defaults to `1`.
- `crypto/ecdsa.c:692–710` — deterministic `k` via `init_rfc6979` / `generate_k_rfc6979`.
- `crypto/ecdsa.c:741` — additional `generate_k_random` used for **blinding** side-channel randomization of intermediate scalars, not as the ECDSA nonce when RFC6979 is on; that random comes from `random32` → hardware `random_buffer`.
- `crypto/zkp_ecdsa.c` uses `secp256k1_nonce_function_rfc6979` for the libsecp256k1-zkp path.
- If `USE_RFC6979` were ever defined to `0`, signing would use pure random `k` from the same TRNG path (`ecdsa.c:716–717`) — still not a software-PRNG fallback.
