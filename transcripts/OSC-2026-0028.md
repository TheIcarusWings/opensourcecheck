## Architecture relevant to entropy

Bitkey firmware is multi-image:

| Image | SoC | Crypto RNG source (meson) |
|-------|-----|---------------------------|
| `w3-core` / `w1` application | EFR32MG24 | `firmware/lib/crypto/src/efr32/secure_rng.c` → `sl_se_get_random` |
| `w3-uxc` application / loader | STM32U5 | `firmware/lib/crypto/src/stm32/rng.c` → MCU TRNG → HMAC-DRBG |
| Host/unit tests | POSIX | OpenSSL `RAND_bytes` |

Wallet seed code (`firmware/lib/wallet`) is linked into **w3-core** and **w1** (`wallet_dep` in those `meson.build` files), which use **EFR32** crypto — not the STM32 DRBG path. That distinction is essential for the Coldcard-class question (“does seed generation silently use a weak software PRNG?”).

## 3.1 Seed entropy call chain (wallet core — production)

**Seed material**

- `firmware/lib/wallet/src/seed_impl.h:6` — `SEED_SIZE 32` (256-bit seed).
- `firmware/lib/wallet/src/seed.c:21–36` — `master_key_lazy_init`:
  - Try load+decrypt existing seed from filesystem (`wkek_read_and_decrypt`).
  - If missing: `ASSERT(crypto_random(seed->bytes, sizeof(seed->bytes)))` then derive master key and encrypt+store.
- Fail-closed: `ASSERT` on embedded builds invokes `_assert_handler` (`firmware/lib/assert/assert.h:18–22`) if `crypto_random` returns false.

**EFR32 `crypto_random` (wallet path)**

- `firmware/lib/crypto/src/efr32/secure_rng.c:8–21`:
  - Init Secure Engine command context.
  - `sl_se_get_random(&cmd_ctx, data, num_bytes)`.
  - Returns `false` on any SE failure — no software fallback, no timer/UID seed.
- Declared in `firmware/hal/secure-engine/inc/secure_engine.h:40` (Silicon Labs SE manager API).
- Platform wiring: `firmware/lib/crypto/meson.build` `efr32mg24` sources list includes `src/efr32/secure_rng.c` only (no HMAC-DRBG for that platform).
- `firmware/app/w3-core/application/meson.build:51` — `crypto_deps['efr32mg24']`; `:58` — `wallet_dep`.

**Entropy estimate (seed):** nominal 256 bits from SE TRNG. Effective entropy ≈ min-entropy of the Secure Engine TRNG for 32 output bytes — not reduced by a software PRNG seed. Confidence: high on selection; absolute min-entropy not measurable from source alone.

## 3.1b STM32 UX controller path (not wallet seed, still in pack scope for keys/nonces)

UXC uses a different stack:

- `firmware/mcu/stm32u5xx/src/mcu_rng.c:56–100` — configure STM32U5 RNG per AN-4230 / NIST-config constants (`_MCU_RNG_NISTC_CR`, HTCR, NSCR); enable `RNGEN`.
- `:67–80` — `mcu_rng_get`: on seed error (`SECS`) reconfigure; assert SECS clear; wait `DRDY`; return `RNG->DR`. **Does not check `CECS`.** CED is configured disabled in `_MCU_RNG_CR_MSK` (`:29`, `:38`) as part of the documented NIST config mask.
- `firmware/lib/crypto/src/stm32/rng.c:23–36` — `trng_random` fills from `mcu_rng_get`.
- `:39–51` — `crypto_random_init`: once, pull **64 bytes** of TRNG (`2 * SHA256_DIGEST_SIZE`) and `crypto_hmac_drbg_init` — comment notes double entropy as bias guard.
- `:54–62` — subsequent `crypto_random` is pure HMAC-DRBG generate; always returns `true` after init (errors surface as ASSERT inside DRBG if state invalid).
- `firmware/lib/crypto/src/stm32/hmac_drbg.c:12–15` — NIST SP 800-90A HMAC-DRBG; intentionally **no reseed counter**; comment argues 2^48 reseed interval is unreachable on-device. `crypto_hmac_drbg_reseed` exists (`:72–81`) but is **not called** after init from `rng.c`.
- Init called from `firmware/app/w3-uxc/application/main.c:162` and loader `:157`.

This path backs UXC crypto (IVs, glitch delays, non-wallet secrets on that chip). It is **not** the BIP-32 seed creator for w3-core. No silent software LCG: if TRNG init fails, `ASSERT(trng_random(...))` faults.

## 3.2 / 3.3 Selection and build flags

- Platform selection is compile-time via Meson `crypto_platform_configs` (`firmware/lib/crypto/meson.build:1–78`): mutually exclusive source sets per SoC — no runtime “use soft RNG if hard fails” switch for seed.
- Host/posix uses OpenSSL (`src/posix/secure_rng.c:10–11`) — simulator/tests only.
- No flag analogous to `MICROPY_HW_ENABLE_RNG=0` found that rewrites production `crypto_random` to a userspace PRNG seeded from UID/timers.
- UI-only `ui_rand` in `mfg_starfield_fps.c` is display animation, not key material.

---

## 3.4 / 3.5 PRNG seeding, fallbacks, health

- EFR32: no intermediate PRNG; direct SE TRNG. Failure → `false` → seed ASSERT.
- STM32: HMAC-DRBG seeded once from 512 bits of TRNG. No UID/timer seed. No runtime fallback to weak PRNG.
- Health testing: `dudero` statistical checks exist (`firmware/lib/secutils`) and are used from crypto **command/test** paths (`crypto_test.c`, `crypto_cmd.c`), not as online gates on every `crypto_random` call in production seed generation.
- Continuous equal-sample FIPS-style filter (as in Trezor’s STM32 code) is **not** present in `mcu_rng_get`; recovery is limited to SECS reconfigure.

## 3.6 Signing nonces

**secp256k1 ECDSA (shared `ecc.c`, used with libsecp256k1 on EFR32 path)**

- `firmware/lib/crypto/src/ecc.c:184–207` — `crypto_ecc_secp256k1_ecdsa_sign_hash32` calls  
  `secp256k1_ecdsa_sign(..., NULL, NULL)` → **libsecp256k1 default nonce function = RFC 6979**. Blinding seed for context randomization still comes from `crypto_random` (`:194–197`); failure aborts sign.

**BIP-340 Schnorr**

- `firmware/lib/crypto/src/ecc.c:103–128` — `auxiliary_rand` from `crypto_random` (32 bytes), then `secp256k1_schnorrsig_sign32`. Weak auxiliary randomness would not by itself yield the private key the way ECDSA nonce reuse does; BIP-340 remains safe if aux is weak, but here aux is SE TRNG on core. Post-sign verify (`:130–140`) as defense-in-depth.

**STM32 P-256 (device identity / non-Bitcoin curves on UXC)**

- `firmware/lib/crypto/src/stm32/ecc.c:160–167` — random `k` via `crypto_ecc_generate_random_scalar` → `crypto_random` (HMAC-DRBG). Explicit comment that `k` must be unique. Not the Bitcoin signing path for user funds on core.
