## 1. Change-output verification — the host cannot supply a change address at all

This is the strongest construction of the five signers audited under this pack.

`core/src/apps/bitcoin/sign_tx/bitcoin.py`, `output_derive_script` (~961–982):

```python
if txo.address_n:
    # change output
    try:
        input_script_type = common.CHANGE_OUTPUT_TO_INPUT_SCRIPT_TYPES[txo.script_type]
    except KeyError:
        raise DataError("Invalid script type")
    node = self.keychain.derive(txo.address_n)
    txo.address = addresses.get_address(input_script_type, self.coin, node, txo.multisig)

assert txo.address is not None
return scripts.output_derive_script(txo.address, self.coin)
```

The device **overwrites** `txo.address` with an address derived from its own keychain. Where
Keystone3 and SeedSigner compare a host-supplied address against a derived one and reject on
mismatch, Trezor never consults the host's address for a change output — it can only be told a
*path*. There is nothing to compare and therefore nothing to spoof.

`core/src/apps/bitcoin/sign_tx/change_detector.py`, `output_is_change` (~45–68), then gates
whether an output counts as change behind seven conjoined conditions:

```python
return (
    self.multisig_fingerprint.output_matches(txo)
    and self.wallet_path.output_matches(txo)
    and self.script_type.output_matches(txo)
    and len(txo.address_n) >= common.BIP32_WALLET_DEPTH
    and txo.address_n[-2] <= _BIP32_CHANGE_CHAIN
    and txo.address_n[-1] <= _BIP32_MAX_LAST_ELEMENT
    and txo.amount > 0
)
```

The path must share a common prefix with the *inputs'* paths (`WalletPathChecker`), the script
type must match the inputs', and for multisig the cosigner fingerprint set must match. So an
attacker cannot nominate an arbitrary in-wallet path as change.

**A defence I have not seen elsewhere.** Earlier in the same function:

```python
if txo.multisig and not common.multisig_uses_single_path(txo.multisig):
    # ... The attacker could randomize the address indices and then demand a
    # ransom from the user to reveal the paths. To prevent this, we require
    # that all xpubs use the same derivation path.
    return False
```

That is a documented mitigation for a *ransom* attack — a compromised host randomising multisig
address indices so the user cannot rediscover their own change without paying. The
`_BIP32_MAX_LAST_ELEMENT = 1_000_000` bound exists for the same reason: it keeps a lost path
brute-forceable. This is threat modelling well beyond the change-spoofing class the pack asks
about.

## 2. Assessment

No defect found in scope. The design removes the attack surface rather than defending it: by
deriving change addresses itself, Trezor makes the host-supplied-change-address class
inapplicable, and the seven-condition gate plus the input-path prefix requirement close the
attacker-nominates-a-path variant.

## Scope limits, stated plainly

I examined the change-output decision and derivation only. **Not examined in this run:** input
amount provenance and fee sanity (Trezor is the origin of the 2018 SegWit fee-attack advisory
that other wallets in this registry cite, so its current input-verification code deserves its own
record), the `PrevTx` streaming/hashing path, `SignMessage`, Decred and other altcoin
implementations, the `authorization.py` CoinJoin path, and firmware update integrity. A future
attestation should cover input verification specifically.
