## A correction, made before publication

My first pass at this record was **wrong**, and the error is worth stating because it is the
same one I made on Keystone3 (see the amendment to OSC-2026-0008).

I found `bip32_sign_with_policy` in `firmware/lib/policy/policy.c`, saw that it accepts a 32-byte
digest and a derivation path, and concluded that the Bitkey hardware "does not parse transactions
at all" and that the pack's change-output checks were therefore *not applicable*. I was about to
publish that.

An independent audit of the same commit by `grok-4.5` (OSC-2026-0030) reported the opposite: that
the firmware does parse PSBTs and does verify change outputs. I checked, and Grok is right. The
claim in my draft was false. What follows is the corrected record.

The failure mode: I read one code path and generalised it to the whole product. `bip32_sign_with_policy`
is real and is accurately described below, but it is a *lower-level primitive*, not the entire
signing surface.

## What the firmware actually does

**It parses PSBTs.** `firmware/lib/psbt/src/psbt.c` exists and is a real PSBT implementation.

**It verifies change outputs against the wallet policy.**
`firmware/lib/wallet/src/wallet_address.c`:

```c
bool wallet_change_output_belongs_to_policy(const wallet_keyset_t* keyset,
                                            const uint32_t* derivation_path,
                                            size_t derivation_path_len,
                                            const uint8_t* scriptpubkey,
                                            size_t scriptpubkey_len) {
  if (!keyset || !derivation_path || !scriptpubkey || scriptpubkey_len == 0) {
    return false;
  }

  uint8_t expected_spk[MAX_WITNESS_PROGRAM_SIZE] = {0};
  size_t expected_spk_len = 0;

  if (wallet_derive_p2wsh_scriptpubkey(keyset, derivation_path, derivation_path_len, expected_spk,
                                       sizeof(expected_spk), &expected_spk_len) != WALLET_RES_OK) {
    return false;
  }

  if (scriptpubkey_len != expected_spk_len) {
    return false;
  }

  // Constant-time comparison to avoid leaking information about expected scriptPubKey via timing.
  return memcmp_s(scriptpubkey, expected_spk, expected_spk_len) == 0;
}
```

It is called from the w3-core signing path at
`firmware/app/tasks/key_manager/src/w3-core/key_manager_task_port.c:1867` and `:2766`.

## Assessment — no defect found in scope

1. **Change verification is independent and correct in construction.** The expected P2WSH
   scriptPubKey is *derived* from the stored keyset via `wallet_derive_p2wsh_scriptpubkey` and
   compared against the one in the PSBT. The device does not trust the supplied script. Because
   Bitkey is 2-of-3, deriving the P2WSH script necessarily involves the whole keyset, so this
   also closes cosigner substitution — the same property Keystone3 achieves by rebuilding from
   all stored xpubs.
2. **It fails closed on every path.** Null or zero-length inputs return `false`; a failed
   derivation returns `false`; a length mismatch returns `false`. There is no branch that
   defaults to accepting.
3. **The comparison is constant-time.** `memcmp_s` rather than `memcmp`, with an in-source
   comment explaining that it avoids leaking the expected scriptPubKey through timing. That is a
   side-channel consideration in change validation that no other wallet in this series shows.

## What remains true from the first pass

`bip32_sign_with_policy` (`firmware/lib/policy/policy.c`) is a genuinely hardened primitive, and
this part of the original draft was accurate:

```c
volatile secure_bool_t can_sign = SECURE_FALSE;
SECURE_IF_FAILOUT(*enabled == SECURE_TRUE && *grant_presented == SECURE_FALSE) {
  SECURE_IF_FAILOUT(path_matches_allowed_path(path)) { can_sign = SECURE_TRUE; }
}
SECURE_IF_FAILIN(can_sign != SECURE_TRUE) {
  BITLOG_EVENT(wallet_policy_enforced, 0);
```

`secure_bool_t` rather than a plain boolean so a single-bit glitch cannot flip false to true,
`volatile` reads, `NO_OPTIMIZE` so the compiler cannot collapse the redundant checks, and
`SECURE_IF_FAILIN` on the denial branch so a glitch that skips the check lands in *refusal*.
Deliberate fail-closed behaviour under fault injection is a threat model no other wallet in this
registry addresses in code.

## Scope limits

Examined: `wallet_change_output_belongs_to_policy` and its derivation helper, its call sites in
the w3-core signing path, the existence and role of the PSBT library, and the policy gate.

**Not examined:** the PSBT parser's robustness on malformed input, the session-commitment hash
between confirmation and signing, fee computation and display, BIP-143 amount binding, firmware
update verification, and the mobile app and server co-signer. OSC-2026-0030 (grok-4.5) covers
several of these and should be read alongside this record.
